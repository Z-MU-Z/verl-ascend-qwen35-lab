- public `torch_npu 2.8.x` is not enough to realize the PR-reported `torch 2.10` matrix

- therefore do not treat the smoke test as the default next step while the environment is still on the fallback line

## Secondary Blockers And Pitfalls

### 1. Remote GitHub access is unreliable

Direct remote installs such as:

```bash
pip install git+https://github.com/huggingface/transformers.git@cc7ab9be
```

can fail with GitHub timeout from the cluster.

Mitigation already prepared:

- download source tarballs locally
- upload them to `/shared/dist`
- install from `/shared/dist/...tar.gz`

### 2. `vllm==0.18.0` on PyPI tries to move the environment

When installed directly in the shared env, it pulls a dependency chain that wants:

- `torch 2.10.0`
- `torchaudio 2.10.0`
- `torchvision 0.25.0`
- `numpy 2.x`
- many CUDA-oriented or generic dependencies

This is one reason the env was temporarily pulled into a bad state before being restored.

### 3. `vllm-ascend@54879467` uses build isolation

Its `pyproject.toml` currently asks for build requirements including:

- `torch==2.9.0`
- `torch-npu==2.9.0`
- `transformers>=4.57.4`
- `triton-ascend==3.2.0`

This matters because even if runtime pinning says one thing, build isolation may silently try to create another stack in a temporary env.

### 4. Shared NFS git worktree can behave oddly

Seen already:

- temporary stale states
- `git pull` occasionally hanging or behaving strangely on shared worktree
- earlier untracked files from `rsync` blocked pulls

Do not assume a hang means authentication. It may be the shared worktree itself.
